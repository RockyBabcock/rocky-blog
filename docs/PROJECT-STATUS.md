## 1. 项目是什么

Rocky Blog 是一个以内容创作、阅读和发现为中心的**高视觉表现力静态个人博客**。它应当同时具备：

- **内容质量：** 文章、主题、分类、标签、周刊与系列内容组织清晰，适合长期积累。
- **阅读体验：** 排版、导航、搜索、目录、阅读进度、收藏和响应式阅读体验完整。
- **视觉识别度：** 有成熟的编辑式设计、鲜明的版面节奏、精致的视觉细节和适度动效，不是空白的功能原型，也不是通用后台仪表盘。
- **可维护性：** 通过 Markdown 和配置文件管理内容，以静态构建和静态托管为主，不依赖 CMS、账号系统、数据库或常驻应用服务器。

技术基线是 Astro 7、React 19、TypeScript、Tailwind CSS 4、Pagefind、Nanostores 和 Motion。准确依赖版本以 `package.json` 和 `pnpm-lock.yaml` 为准。

## 2. 维护者已经明确的核心要求

以下要求是后续设计、开发、代码审查和 Agent 执行任务时必须遵守的产品约束。

### 2.1 保留既有页面与模块

- **不得为了“简化”“清理”或追求极简而删除既有首页模块、页面入口或已经建立的阅读能力。**
- 可以重排、重构、拆分、合并视觉容器、增加信息层次和补充交互，但必须保证原有内容与功能仍然可访问。
- 不得通过隐藏模块、减少展示内容、移除入口或削弱信息量来制造留白。
- 删除现有功能、改变用户可见行为或缩小产品范围，必须先取得维护者明确决策，并同步更新产品范围文档。

### 2.2 视觉表现力是当前持续优先事项

维护者已明确反馈：界面不能显得空荡、单薄、功能稀少或缺乏表现力。后续 UI 工作应主动改善视觉层次和细节丰富度，而不是只做代码层面的简化。

设计方向固定为：

**Premium Editorial × Contemporary Magazine × Sakura Botanical × Celestial Details**

具体要求：

- 以编辑式排版、清楚的信息层级、稳定的阅读版心和有节奏的留白为基础。
- 各首页模块和主要页面应有自己的版面性格；可使用不对称网格、分栏、时间线、横向轨道、索引式列表、特色封面、层叠表面和节奏变化，避免所有内容都变成同一种卡片。
- 在适当位置加入精致而有秩序的细节，例如眉题、编号、微型标签、细分隔线、边框、角标、几何线条、轻纹理、植物枝叶、樱花花瓣、星点、轨道和星座式图形。
- 丰富度应来自**有设计意图的层次、结构和细节**，不是无目的堆叠阴影、渐变、卡片、粒子或装饰。
- 视觉上要避免“过多空白导致页面缺乏内容感”，也要避免“装饰过多造成阅读噪声”；应逐模块调整比例、密度和节奏。
- 视觉优化不得损害正文可读性、操作可发现性、响应式布局、键盘使用、性能或 reduced-motion 支持。
- 避免动漫 / 漫画 / kawaii / Q 版视觉、幼态插画、廉价霓虹、随机色值和无目的玻璃拟态。
- 复用现有 Design Tokens、主题变量、排版和间距体系，不在每个组件里另造局部设计系统。

**视觉验收至少包括：** 首页各模块仍完整；桌面与移动端布局都成立；浅色与深色主题可读；重点与次要信息层级清楚；装饰不遮挡内容或交互；减少动态效果时依然完整可用。

### 2.3 功能必须真实、完整且有边界

- 新增的按钮、菜单、弹层、筛选和切换必须执行明确动作，不能只提供视觉占位。
- 交互状态应有加载、空状态、错误和不可用时的合理反馈。
- 新功能应尽量沿用已有组件、状态 store、工具函数和数据模型；先搜索相同能力，避免平行实现。
- 不为了增加“功能数量”引入重复入口、无必要的后台服务或复杂依赖。
- 优先保证静态生成、首屏性能、可访问性和长期维护成本。

### 2.4 Markdown 是主要内容交付形式

- 文章以仓库中的 Markdown 文件作为内容源，主要路径为 `src/content/blog/`。
- 维护者可以使用 MuseAI 或其他写作工具辅助生成文章，再将经过校验的 `.md` 文件加入仓库。
- 内容必须遵守 `src/content.config.ts` 的 frontmatter schema、目录结构、分类映射、稳定 slug 和翻译关联规则；不要为了迁就生成内容而擅自增加 schema 不支持的字段。
- 内容生成工具不是网站运行时依赖。MuseAI 不应被理解为 Rocky Blog 的 CMS、后端服务或在线写作后台。
- 文章发布流程是：生成 / 编辑 Markdown → 校验 frontmatter、文件路径、分类、链接和语言镜像 → 提交仓库 → 运行检查和静态构建 → 部署静态产物。
- 不要编造代码执行结果、项目经验、数据、引用或翻译完成状态。

### 2.5 多语言范围固定为四种

| Locale | 语言 | 路由 |
| --- | --- | --- |
| `zh` | 中文，默认语言 | 无语言前缀 |
| `en` | English | `/en/` |
| `ja` | 日本語 | `/ja/` |
| `fr` | Français | `/fr/` |

- UI 字典、导航、按钮、搜索、设置、空状态、提示和日期格式应尽可能完整覆盖四种语言。
- 新增或修改 UI 文案时，要同步检查四种 locale。
- 不要添加韩语。
- UI 支持四种语言，不代表每篇文章都有四种译文；译文必须以真实内容文件为准，缺失时按当前回退逻辑处理，不得伪装成已翻译。

### 2.6 静态优先与隐私边界

- Astro 负责文件路由、内容生成和静态 HTML；React 仅用于确有交互需要的 islands。
- 默认通过 YAML、Markdown 和构建流程完成内容管理与发布。
- 不引入账号、云数据库、服务端阅读历史、云书架或跨设备同步，除非维护者重新决策。
- 阅读历史、阅读设置、系列进度和 Reading Shelf 收藏均为浏览器本地数据。
- AES-256-GCM 是构建期静态加密，不是服务端鉴权、DRM 或私有内容托管。
- 完整保留范围和非目标以 [产品范围](./PRODUCT-SCOPE.md) 为准。

## 7. Agent / 开发者工作流程

### 开始任务前

1. 读取仓库根目录的 `AGENTS.md`。
2. 读取本文和 [PRODUCT-SCOPE.md](./PRODUCT-SCOPE.md)。
3. 根据任务继续阅读相应架构文档；例如内容任务阅读 `02-content-system.md`，路由 / 语言任务阅读 `03-routing.md` 与 `11-i18n-and-seo.md`，视觉任务阅读 `05-ui-components.md`、`07-theme-system.md`、`08-animation-system.md` 和 `09-styling.md`。
4. 检查当前分支、HEAD、相关实现和测试；不要只依赖历史聊天、旧截图或旧提交。

### 实施任务时

- 先明确目标、涉及范围、验收条件和风险。复杂任务先给出简短计划。
- 先搜索已有组件、store、hooks、配置项和工具函数，再决定是否新增抽象。
- 先确认产品范围，再改代码；不得以技术便利为理由越过维护者明确决定。
- 每次只处理目标范围，避免无关重构和大面积格式化。
- UI 修改同时考虑桌面、平板、移动端、浅色 / 深色、键盘和 reduced-motion。
- 新 UI 文案维护四种语言；新内容校验 frontmatter、分类映射、稳定 slug 和翻译关联。
- 不要删除模块、功能入口、测试或历史资料来让检查通过；先查清引用和产品决策。
- 对动态导入、Astro islands、内容发现、路由生成和运行时注册进行检索；不能仅凭单条 Knip 未使用报告删除文件。

### 变更后

- 产品决策变化：先更新 `docs/PRODUCT-SCOPE.md`，再同步 README、Agent 规则、用户指南和相关架构说明。
- 架构变化：更新对应 `docs/overview/` 章节。
- 写作或配置流程变化：更新 `GETTING-STARTED.md` 与 Blog Writer Skill。
- 状态只有在实现、检查或部署结果实际发生变化时才更新本文；记录日期、commit、验证命令和证据。
- 不要把“计划做”“代码已写”“本地验证通过”“CI 通过”“已部署”混成同一个状态。

## 8. 状态用语与完成定义

统一使用以下状态：

- **Planned / 计划中：** 维护者已批准，但尚未开始实施。
- **In progress / 进行中：** 已开始修改，有明确任务范围。
- **Blocked / 阻塞：** 由于权限、外部依赖、产品决策或失败检查无法继续，并说明阻塞原因。
- **Needs decision / 需要决策：** 仍需维护者选择，Agent 不得擅自决定。
- **Deferred / 暂缓：** 已决定暂不实施。
- **Done / 已完成：** 代码或文档已合入目标分支，适用检查已运行并通过；若需要部署，还必须有部署成功证据。

所有交付汇报至少说明：**做了什么、改了哪些文件、验证了什么、验证结果、尚未验证 / 未解决事项、对应 commit**。没有证据的项目不得标记为 Done。
